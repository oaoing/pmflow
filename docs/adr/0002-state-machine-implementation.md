# ADR-0002: 상태머신 구현 방식

- 상태: 수용됨 (Accepted)
- 날짜: 2026-09-06 (제안) / 2026-09-06 (수용)
- 관련: [domain-model.md](../domain-model.md) 4장(상태 전이), [ADR-0003](0003-numbering-strategy.md)(채번 전략)

## 컨텍스트

4개 엔티티 중 3개(점검계획 PLAN, 점검실행 CHECK, 정비의뢰 ORDER)가 상태를 가지며,
허용 전이는 [domain-model.md](../domain-model.md) 4장에 매트릭스로 확정되어 있다.

전이 규칙의 특징:

- 대체로 선형이다: `CREATE → CONFIRM → INPROGRESS → CLOSE`, 각 단계에서 `CANCEL` 분기.
- 병렬 상태, 복합 상태, 타임아웃 자동 전이 같은 고급 요구가 없다.
- 전이의 **선행조건(guard)** 은 상위 엔티티 상태에 의존한다 (예: CHECK 생성은 상위 PLAN이 `CONFIRM`일 때만).
- 전이의 **부수효과** 는 채번, 타임스탬프 기록 등 서비스 계층 책임과 겹친다.

제약과 목표:

- MVP 컷라인 — 최소 의존성, 낮은 러닝커브.
- 상태 전이 단위테스트 20~30개가 프로젝트의 핵심 "볼거리". 전이 규칙을 **순수 로직으로 격리**해 테스트하기 쉬워야 한다.
- 채번·정합성 규칙을 서비스 계층 단일 지점에서 다루기로 한 방침과 일관성을 유지한다.
- 문서(4장 매트릭스)와 코드가 1:1로 대응되어 검증 가능해야 한다.

## 결정 동인

1. 테스트 용이성 — 전이 규칙을 프레임워크·DB·스프링 컨텍스트 없이 검증할 수 있는가.
2. 문서-코드 추적성 — 매트릭스를 보고 구현이 맞는지 바로 대조되는가.
3. 무게 — 의존성, 설정량, 영속화 복잡도.
4. 확장 여지 — 이력 추적, 도메인 이벤트 발행을 나중에 얹을 수 있는가.

## 검토한 선택지

### A. Spring Statemachine

- 장점: 표준 라이브러리, 가드/액션/이벤트 개념 내장, 시각화 지원.
- 단점:
  - 엔티티 인스턴스마다 상태머신을 build/restore 해야 함(`StateMachineFactory`, `StateMachinePersister`) — 3개 엔티티 각각 설정.
  - 영속 엔티티의 상태 컬럼과 상태머신 상태의 동기화가 번거롭다.
  - 테스트에 스프링 컨텍스트 또는 무거운 셋업 필요 → 20~30개 테스트가 느려지고 장황해짐.
  - 이 규모(선형 전이, 상태 5개)에는 명백히 과설계.

### B. Enum 기반 전이 테이블 (직접 구현) — 채택

- 허용 전이를 엔티티별 `EnumMap<Status, Set<Status>>` 로 선언.
- `transition(current, target)` 이 테이블을 조회해 허용 여부만 판정하고, 불가 시 예외.
- 가드(선행조건)와 부수효과는 서비스 계층이 담당 — 상태머신은 "전이 가능성" 판정에만 집중.
- 장점:
  - 전이 테이블이 4장 매트릭스와 시각적으로 1:1 대응.
  - 순수 함수 → `assertThatThrownBy(() -> sm.transition(CLOSE, INPROGRESS))` 식으로 즉시 테스트.
  - 의존성 0, 설정 0.
  - 직접 만든 엔진 → 트러블슈팅/설계 서사 확보(ADR·README 소재).
- 단점:
  - 전이별 부수효과 오케스트레이션은 여전히 서비스가 직접 해야 한다(상태머신이 대신 안 해줌).
  - 이력 추적·이벤트 발행은 별도로 얹어야 한다.

### C. 서비스 메서드 내 if/switch 인라인 검증

- 장점: 가장 단순, 코드량 최소.
- 단점: 전이 규칙이 여러 메서드에 분산 → 매트릭스와 대조 불가, 테스트가 서비스 전체 경로를 타야 함. 규칙이 3엔티티로 늘면 급격히 산만해진다.

### D. State 패턴 (GoF, 상태별 클래스)

- 장점: 상태별 행위 캡슐화.
- 단점: 상태 5개 × 엔티티 3개 = 클래스 폭발. 전이 규칙이 여러 클래스에 흩어져 오히려 파악이 어려움. 행위 다형성이 필요 없는 이 도메인엔 부적합.

## 결정

**B. Enum 기반 전이 테이블**을 채택한다.

구현 방향:

- 상태값은 [domain-model.md](../domain-model.md) 3장의 공유 `Status` enum을 사용하고,
  **전이 테이블은 엔티티별로 분리**한다 (`PlanStateMachine`, `CheckStateMachine`, `OrderStateMachine` 또는 설정 상수 3벌).
- 공통 판정 로직은 재사용:
  ```
  interface StateMachine<S> {
      // 허용되면 target 반환, 아니면 IllegalStateTransitionException
      S transition(S current, S target);
      boolean canTransition(S current, S target);
      Set<S> nextStates(S current);
  }
  ```
- **가드**(상위 PLAN=CONFIRM, 상위 CHECK∈{INPROGRESS,CLOSE} 등)는 상태머신 밖, 서비스 계층에서 전이 호출 전에 검증한다.
- **부수효과**(채번, `approved_at`/`started_at`/`closed_at` 기록)는 서비스 계층 트랜잭션 내에서 처리한다.
- 전이 실패 예외는 `domain` 패키지에 정의하고, HTTP 매핑은 `api-conventions.md`에서 담당한다.

## 결과

### 긍정적

- 전이 규칙 테스트가 빠르고 선언적. 매트릭스 셀 하나 = 테스트 케이스 하나.
- 새 상태·전이 추가 시 테이블 한 줄 수정 + 테스트 한 줄 추가로 끝.
- 외부 의존성 없음. 빌드·기동 시간에 영향 없음.

### 부정적 / 트레이드오프

- 상태머신이 부수효과를 오케스트레이션하지 않으므로, 서비스 메서드가 "가드 검증 → 전이 판정 → 부수효과 → 저장" 순서를 매번 직접 조립해야 한다. → 공통 템플릿 메서드로 완화.
- 상태 전이 이력, 도메인 이벤트는 이 ADR 범위 밖. 필요 시 전이 지점에 훅을 추가하는 별도 결정으로 다룬다.

### 재검토 트리거

다음 중 하나가 발생하면 A(Spring Statemachine) 또는 이벤트 소싱을 재검토한다:

- 상태 있는 엔티티가 5개를 넘거나 상태 수가 엔티티당 8개를 넘는 경우.
- 승인 위임, 타임아웃 자동 전이, 병렬 하위 상태 등 워크플로우 요구가 생기는 경우.
- 전이 이력·감사 요구가 핵심 기능으로 승격되는 경우.
