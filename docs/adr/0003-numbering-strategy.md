# ADR-0003: 채번 전략과 동시성 제어

- 상태: 수용됨 (Accepted)
- 날짜: 2026-09-06 (제안) / 2026-09-06 (수용)
- 관련: [domain-model.md](../domain-model.md) 6장(채번 규칙) · 정합성 규칙 R05 · ADR-0004(통합테스트)

## 컨텍스트

3종의 업무 ID를 규칙에 따라 발급한다.

| 엔티티 | 형식 | scope (리셋 단위) |
|--------|------|-------------------|
| 계획 PLAN | `PM-YYYYMM-nnn` | 연·월 |
| 실행 CHECK | `PM-YYYYMM-nnn-mmmm` | 상위 계획 |
| 의뢰 ORDER | `OD-YYYYMM-nnn` | 연·월 |

요구사항:

- **R-1 유일성**: 동일 scope 내 중복 번호가 절대 발생하지 않는다.
- **R-2 리셋**: `nnn`은 매월 001로 리셋. `mmmm`은 계획별 0001로 시작.
- **R-3 연속성**: 번호는 가능한 한 연속이어야 한다(결번 최소화). 단, 완전 무결까지는 요구하지 않는다.
- **R-4 단일 진입점**: 모든 채번은 서비스 계층의 한 컴포넌트에서만 수행한다.
- **R-5 멀티 인스턴스 안전**: 컨테이너로 배포되며 인스턴스가 2개 이상일 수 있다. 애플리케이션 프로세스 락으로는 부족하다.
- **R-6 처리량**: 채번이 쓰기 경로의 병목이 되지 않아야 한다(k6 p95 목표는 별도 관리).

채번은 엔티티 생성 트랜잭션의 크리티컬 섹션이며, 동시 요청 시 race condition이 발생하는 전형적 지점이다.

## 결정 동인

1. 동시성 안전성 (R-1, R-5) — 최우선.
2. 구현·운영 단순성 — MVP 컷라인.
3. 처리량 (R-6).
4. 관측 가능성 — 실패 시 원인 추적이 쉬운가.

## 검토한 선택지

| 선택지 | 요지 | 평가 |
|--------|------|------|
| A. `SELECT MAX(seq)+1` | 현재 최대값 조회 후 +1 | ❌ 조회~삽입 사이 race(TOCTOU). 유니크 제약이 있어도 동시성 하에서 실패율이 높다 |
| B. DB IDENTITY / AUTO_INCREMENT | 컬럼 자동 증가 | ❌ 전역 단조 증가만 가능. 월별 리셋(R-2)·포맷 불일치 |
| C. DB 시퀀스 오브젝트 (월별 동적 생성) | `CREATE SEQUENCE pm_202609` | △ 런타임 DDL, 시퀀스 정리 부담, 벤더 종속 |
| **D. 전용 시퀀스 테이블 + 행 잠금** | `numbering_sequence(scope_key, last_seq)` 를 `SELECT … FOR UPDATE` 후 증가 | ✅ **채택**. 표준적, 멀티 인스턴스 안전, scope_key 단위로만 직렬화 |
| E. 전용 시퀀스 테이블 + 원자적 UPDATE | `UPDATE … SET last_seq = last_seq + 1 … RETURNING` | ✅ D의 구현 변형. 잠금 보유 시간이 더 짧다 (구현 시 우선 검토) |
| F. 분산 락 (Redisson 등) | 외부 락 서비스 | ❌ 인프라 추가. 이 규모엔 과함 |
| G. Hi/Lo · pooled optimizer | 블록 단위 선점 | ❌ 결번 대량 발생 → 업무 ID로 부적합(R-3 위배) |

## 결정

**D(전용 시퀀스 테이블 + 행 잠금)** 를 채택하고, 구현은 **E(원자적 UPDATE)** 를 우선한다.

### 구조

```
numbering_sequence
  scope_key   VARCHAR  PK   -- 예: "PM-202609", "PM-202609-001", "OD-202609"
  last_seq    INT           -- 마지막으로 발급한 번호
```

- **단일 진입점**: `NumberingService.next(scopeKey) → long`. 모든 엔티티 서비스가 이것만 호출한다.
- **원자적 증가**: `UPDATE numbering_sequence SET last_seq = last_seq + 1 WHERE scope_key = :k` → 갱신된 값 조회. row가 없으면 `INSERT`(upsert, 경합 시 유니크 제약으로 1건만 성공 후 재시도).
- **트랜잭션 경계 분리**: 채번은 `REQUIRES_NEW`로 즉시 커밋한다. 본 엔티티 트랜잭션이 길어도 시퀀스 행의 잠금 보유 시간을 최소화한다.
- **최종 안전망**: 각 엔티티 테이블의 업무번호 `code` 컬럼에 `UNIQUE` 제약(PK는 대리키, [architecture.md](../architecture.md) 결정 A). 채번 로직에 결함이 있어도 DB가 중복 삽입을 거부한다(방어적 이중화).
- **자릿수 초과**: `nnn > 999` 또는 `mmmm > 9999`이면 `NumberingOverflowException`. 자릿수를 자동 확장하지 않는다 — ID 길이 안정성을 우선한다. MVP 트래픽에서 도달 불가하나 조용히 넘어가지 않고 명시적으로 실패시킨다.

### scope_key 설계

| 엔티티 | scope_key | 경합 특성 |
|--------|-----------|-----------|
| PLAN | `PM-{YYYYMM}` | 월 단위 단일 행. 계획 등록은 저빈도라 수용 가능 |
| CHECK | `PM-{계획의 YYYYMM}-{nnn}` | 계획별 분산. 서로 다른 계획의 실행 생성은 경합하지 않음 |
| ORDER | `OD-{YYYYMM}` | 월 단위 단일 행. 정비의뢰 등록도 저빈도 |

## 결과

### 긍정적

- 멀티 인스턴스 배포에서 안전(R-1, R-5).
- 잠금 범위가 scope_key 행으로 한정 — CHECK 채번은 계획별로 완전 분산.
- 채번 로직 결함이 있어도 DB 유니크 제약이 최후 방어선.
- 재현·설명이 쉬운 표준 패턴 → 통합테스트로 회귀 방지 가능.

### 트레이드오프

- **결번 허용 (결정됨)**: 채번 커밋 후 본 트랜잭션이 롤백되면 그 번호는 버려진다. 월 시퀀스의 결번은 업무상 허용한다 — CMMS/ERP의 전표·작업지시 번호가 취소분으로 결번이 생기는 것과 동일하다. 무결(no-gap)을 보장하려면 시퀀스 잠금을 엔티티 생성 트랜잭션 전체 동안 보유해야 하고, 이는 `REQUIRES_NEW` 설계 및 처리량 목표(R-6)와 상충한다. 결번 발생은 감사 로그로 추적 가능하게 남긴다.
- **월별 단일 행 경합**: PLAN·ORDER 채번은 같은 달이면 한 행에 직렬화된다. 두 엔티티 모두 저빈도라 수용한다.
- `numbering_sequence` 테이블을 별도로 운영·마이그레이션해야 한다.

### 재검토 트리거

- k6에서 채번이 p95 병목으로 측정되면 → scope_key 세분화, 또는 블록 할당(G, 결번 허용 전제).
- 번호 무결(no-gap)이 규제/감사 요구로 승격되면 → 채번을 본 트랜잭션에 합치고 경합을 감내하는 방식으로 회귀.
- DB를 PostgreSQL이 아닌 것으로 바꾸게 되면 `RETURNING` 가용성 재확인.
